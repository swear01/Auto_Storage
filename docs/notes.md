## Gotchas

- **網路邏輯一律伺服器端**;客戶端靠封包同步,絕不在客戶端保存儲存狀態。
- **Crafting Terminal Transform / Stations 契約**：四頁固定為Storage、Craftable、Transform、Stations。Transform使用一個server-owned transient input與explicit ×1/×8/×64/Max提交；Shift-click後輸入仍在上方slot可見，amount strip也留在上方。Auto只顯示exact input全部用途，不預選、不執行，明確target只篩同一input，玩家必須點whole use card；離頁/關閉會原樣退回未轉換input。Target側欄持續顯示並支援localized search、page、wheel與middle reset，target名稱描述produced resource而非代表物；直接Fuel card不顯示多餘的Direct，timed card第二行才顯示station/work來源；不另設下方selected preview。Fuel/Brew/FE/Mana/Source等能源與Axe Uses都是Core ledger中的typed resource，但Terminal分類不同：前者在Energy，Axe Uses在Other，Processing只顯示internal `station_work`加工值。runtime Fuel依目前burn time，工具依可用耐久，modded provider可註冊需要Processing work的timed transform。Stations只分**Processing Stations**與**Instant Stations**：Processing取得較大寬度並以最多三欄顯示，安裝aggregate count疊在物品上、累積work水平並列；可依exact variant rate累積安裝到`Integer.MAX_VALUE`，prototype固定count 1並另存long aggregate。Instant每descriptor最多一台，只解鎖配方、不製造假能量，因此使用緊密icon grid。兩區依可用高度計算rows，保留explicit previous/next與panel-local wheel paging；Processing稀疏末列維持固定欄寬與靠左靠上；inventory旁panel只顯示type capacity。Stations搜尋只合併兩區，不得再顯示舊Consumables/Fuel reserves。背包機器shift-click一律按exact descriptor路由，不受目前station頁碼影響。所有轉換、station work與recipe item/typed/catalyst/remainder/output仍走同一simulate-then-commit transaction。
- **Terminal cycle/status/reset 契約**:所有 cyclic value selector 都是 left-next/right-previous/wheel-down-next/wheel-up-previous/middle-reset；reset defaults 為 Name、Ascending、Search Sync Off、Auto Focus On、Item resource view、Auto Transform Target、Player Craft Output及既有 player-source default，且必須送 explicit server button action。Transform target sidebar的middle-click同樣重設Auto，但不是cycle button。只有 true boolean on/off control可畫彩色狀態燈；Craft Output、sort/search/resource view/Transform Target等 value selectors不可亮綠/藍 marker。Page tabs可用 neutral selected treatment，但不能冒充 on/off light。Tooltip只顯示控制名稱與目前值，操作手勢寫在指南書。
- **Wrench/connected texture 契約**:Auto Storage 自帶 early Wrench 並加入 `c:tools/wrench`，同時接受其他 mod 在該 tag 的工具。普通主手右鍵只旋轉有方向的 network block；Shift+主手右鍵以正常 loot path拆除任何 network block，含資料Core必須先建立指向同一repository record的recovery mapping，掉落token不得攜帶payload；玩家背包放不下的exact remainder必須掉在世界而不是void。Connected casing在安裝可選Fusion `1.2.12-neoforge-mc1.21.1`的client使用`pieced` layout；未安裝Fusion時主資源的vanilla model必須仍可完整遊玩。client僅在偵測到Fusion後才註冊並強制啟用內建`fusion_connected_casing` overlay；dedicated server不依賴，Prism deploy下載官方Modrinth jar並驗固定SHA-512 `50604fa…365c`，禁止bundle。Gradle dev環境只讓client/data runs選用隔離的`fusionRuntime` source set；server/GameTest維持main source set。官方Modrinth version ID只在`gradle.properties`的`fusion_runtime_version`維護，Gradle、Prism deploy與static tests都讀這個值。**Fusion是mod，不能放進`clientAdditionalRuntimeClasspath`/`dataAdditionalRuntimeClasspath`**：NeoForge 1.21.1只會把該legacy path當一般library，依賴檢查仍會報Fusion未安裝；必須讓Fusion進對應run的標準runtime classpath，`runData`實際成功載入才算驗證。**不要照目前Fusion 1.3 wiki/examples寫schema**：釘選1.2.12的`match_block`只接受單一`block`字串；跨12種network blocks必須寫成12個predicate的array（OR），沒有`blocks`欄位，也沒有`true`/`false` predicates。Bus只為top/side指定連接predicate，ordinary front不需要假`false`。Item models維持普通16×16，bus正面方向語意不能被連接邊框吃掉。
- **Progression/guide 契約**:Starter Core + Storage Terminal + 2x T1 總共只用1 Diamond與一般 overworld black concrete powder/obsidian/copper/redstone/glass/wood，T1不需要amethyst；functional midgame terminal/wrench/buses/remote/T1–T3 不要求 Netherite、Ancient City、Trial Chamber或End completion。T4–T6是選擇性 prestige/capacity upgrades，禁止回到 Diamond Blocks/Netherite Ingots wall；exact matrix見 current connected-progression spec。Patchouli 必須有集中式雙語 Recipe Catalog，en_us/zh_tw category/entry/page/recipe parity，詳細但只講玩家概念，禁止 BFS/packet/hidden slot/wire parity/test totals等實作詞。
- **Recipe ledger 自適應**：正常寬度固定最多四欄，1–4 種在第一列、5–8 種進第二列、9–12 種進第三列並由上緣開始。若 recipe ledger 寬度不足每格 56px，欄數依可用寬度降為 3/2/1；不可為維持四欄而讓材料與數字互相覆蓋。

- **Direct output destination 與 EMI destination 必須分離**:`TerminalOutputDestination` 只控制 terminal 自己的 `×1/×8/×64/Max`，預設 Player，且與 `use player inventory` ingredient source 是兩個獨立 server-synced state。Player 在扣完 player-source ingredients 後先填玩家 36 格、overflow 回 Core；Storage 的 primary outputs 與 crafting remainders 全部只進 Core。完整批次的 type/long capacity 必須先驗證，少一件容量也整筆 no-op；commit 中途拒收則 rollback output 與 Core ingredients。EMI `CraftingDestination.NONE/CURSOR/INVENTORY` 仍是每個 exact request 的權威，不得被 terminal toggle 覆寫。
- **合成 output transaction 不得掉落/吞掉**:INVENTORY destination 先在扣除本次 player ingredients 的 36 格 snapshot 中放 primary output + container remainders，剩餘全規劃回 Core；若 post-extraction Core type/counter capacity 不能完整接受，就在任何 mutation 前拒絕整批。Commit必須重新驗player/Core/station/Axe Energy/typed plan identity；Core ingredients、Core outputs與typed deltas以單一ledger transaction提交，再扣process/Fuel/Axe Energy並套用player inventory/cursor；任何拒絕都不可留下部分Core delta。Requested output 沒有 world-drop fallback，兩邊都滿就是 no-op。CURSOR 只接受單一 exact identity 且不可覆蓋 incompatible carried stack。
- **EMI dependency / compatibility contract**:EMI是release的client-only required dependency，Maven range固定`[1.1.24,2)`；`emi_version=1.1.24+1.21.1`與matching `emi_runtime_version=5sIPA1To`只代表reproducible minimum compile/dev baseline，不得寫成玩家端exact pin。Compile-only與隔離的client/data runtime都使用`maven.modrinth:emi:<version-id>`；compileOnly不會把EMI帶入dedicated runtime，plain `runtimeOnly`仍會污染dedicated GameTest，禁止使用。`scripts/resolve_emi_version.py`直接查官方Modrinth versions API，只接受同Minecraft 1.21.1、NeoForge loader、listed release、在inclusive-min/exclusive-max範圍內且含唯一positive-size primary non-API jar的numeric release；`scripts/resolve_emi_runtime.py <release-version>`再把同一exact `+neoforge` release映射到immutable version ID，缺少或多筆都fail closed。CI與release為minimum及最新相容release各自傳入匹配的human-readable version與Modrinth ID後編譯；client-smoke也以同一映射取得最新runtime。Full jar由`bash scripts/stage_emi_runtime.sh <release-version> <modrinth-version-id>`走Gradle Modrinth Maven落在`build/client-smoke-mods/emi-neoforge-<release-version>.jar`，不得direct curl或直接寫共用`run/mods`；同一Gradle command只可重試一次。解析、映射、下載、ZIP驗證或編譯任一步失敗都直接fail，不得換來源或退回baseline假裝latest通過。Integration只能import`dev.emi.emi.api`公開契約；recipe diagram與search sync adapter都不得import EMI internal screen/runtime package，dedicated server不要求EMI。
- **EMI one-level magic crafting 綁 exact backing identity**:client gate先以backing recipe ID解析目前client holder，要求exact holder identity一致並重新classify；packet再送exact `{containerId,recipeId,amount,destination}`。NONE只選取，CURSOR/INVENTORY由server再次解析目前holder並由adapter重算station/Axe Energy/材料/實際cooking cost，並以「假想扣除本次 player ingredients 後」的 destination capacity 選不超過 request 的最大完整 recipe 數，再 atomic commit。不得信任 client craftability、不得換成同輸出第一個 recipe；Trim必須再綁selected exact output variant，special/dynamic/incomplete或缺少registry context仍fail closed。這是單層立即合成，不包含 RS2 recursive pattern tree，也不為 EMI synthetic favorites 同步整個 network inventory。
- **EMI recipe tree 不是server planner API**:目前最低支援EMI 1.1.24公開API可查input/output recipes、判斷`supportsRecipeTree()`與開啟tree screen，但建立/讀取goal使用runtime-only internal `BoM`/`MaterialTree`，API jar沒有這些類別。禁止直接link、reflection或把client tree當authority。多步驟合成依`docs/superpowers/plans/2026-07-14-modded-recipes-multistep-crafting.md`建立server adapter graph；EMI只作client recipe/tree UI。

## Decisions

- **統一能量池模型**:所有能量池同為 `Map<EnergyType, Long>` 無上限,差異只在來源,降低特例。
- **參考 RS2 而非依賴**:借設計模式,不加為依賴;加任何依賴前先問使用者(minimize deps)。
- **絕不整段照抄 RS2**:授權不同;只取模式自行實作。
- **一網一 core(multi-core 不支援)**:`rebuildNetwork` BFS 碰到第二個 core 即設 `conflicted` → 該 core 停止接受物品 + log 警告,避免雙重容量/非決定性;`isConflicted()` 可查、`tryIncrementalAdd` 在 conflicted 時退回 full rebuild。
- **Bus 吞吐 vs 省資源**:Import/Export bus每個cooldown(10 tick)最多搬一整疊item(≤64)，並各嘗試一次bounded typed transfer(≤1000 native units)；Export只抽目標模擬可接收量。active/passive共用missing-Core 10-tick negative cache，automation probe不可每次重跑最高8192-block BFS。Item在reentrant capacity改變時依actual remainder精確退回，仍拒收才顯式drop；typed overdraw/remainder先還source/Core，仍無法歸還則進persistent Bus escrow並暫停能力，絕不忽略回傳值吞資源。
- **Bus cached core 必須驗證仍連通**:Import/Export bus 的 `cachedCore` 只有在 `core.getConnectedBlocks().contains(busPos)` 時可重用;中間 unit 被拆後不能靠舊 reference 繼續搬物。

## Hardening Pass (2026-06-21)

地毯式 bug 掃描 + 修正。關鍵點與借鏡的 RS2/AE2 模式(僅取模式,未照抄):

- **持久化**:`StorageCoreBlockEntity`只在storage reference改變時把chunk標記dirty；inventory、energy、machine與descriptor mutation直接更新attached `CoreStorageRecord`並讓overworld `CoreStorageRepository` dirty，outer mutation batch只mark一次。BE NBT固定只含`storageId`/`storageSchema`；完整`ItemStack` components與positive `long` count在world data中以每段最多63種的`inventorySegments`保存。拆除只新增recovery UUID→同一storage UUID的indirection，packed item沒有`BLOCK_ENTITY_DATA`或payload fallback。empty attached Core完成移除才刪record；non-empty、missing、corrupt、packed或duplicate狀態絕不建立空白replacement。
- **Core 身分 / remote 綁定**:repository record持有永久storage UUID與network UUID，BE只持有storage UUID/schema reference；packed token只指向同一record。Storage Core不要求特定工具才掉落。Remote Terminal綁`{network UUID,dimension,pos}`並只接受該位置仍解析到同一可用Core；舊coordinate-only binding必須fail closed要求重綁，不可因同座標新Core而靜默存取另一網路。`RemoteTerminalItem.isBound`必須驗齊x/y/z/dimension/UUID並用`tryParse`；重新綁定用`CustomData.update`只覆寫自己的keys。
- **匯流排/合成原子性**:Import bus active pull、passive capability insert 與 `craftItem` 都先 simulate/reserve 再 commit。Passive caller stack 不可 mutation，execute 只 commit simulate 可接受的數量並回 exact remainder。相同 predicate 也保留獨立需求；不同但重疊的 predicates(例如 `#planks` + oak-only，或 strict/partial component predicates)用 joint reservation/max-flow,同一個 item unit 不可算兩次,且要能把 broad match 重新路由給其他變體。conflicted Core、unsupported/dynamic/incomplete recipe 一律 preview 0/拒絕 execute;材料 commit 失敗要 rollback。物品級 crafting remainder(如 milk bucket→bucket)交還玩家。
- **insert/extract 契約**:`insertItem(stack, simulate)` 回傳實際接受量、`extractItem` 回傳實際取出量且庫存只減該量;呼叫端必須尊重回傳值(勿丟棄剩餘 → 否則網路滿時吃物)。
- **數值安全**:`consumeEnergy` / fuel 計算用 exact arithmetic；machine-generated energy 在 `Long.MAX_VALUE` 飽和，load 時負 energy 夾 0。item insert、NBT duplicate merge、fuzzy count 與 Core+玩家 preview 都必須 saturation，不得 wrap。
- **GUI**:隱藏的 `GhostSlot` 以 `isActive()` 停用。Vanilla 在 callback 後才設定 button focus，所以 callback 內清 focus 無效；Crafting screen 必須在 `super.mouseClicked(...)` 返回後清 `AbstractButton` focus並保留目前可見的search `EditBox`。Transform target sidebar與use cards直接使用shared immutable geometry，沒有popup/overlay pass或detached selected preview；target search與Stations search只在各自頁面接收輸入。整張target row/use card使用一致hit box，hidden Stations search不能在Transform上產生ghost tooltip。Stations常駐panel不顯示rate公式或每格說明；Processing的stack count由item decoration擁有，水平amount只顯示累積work，Instant compact cell沒有amount。Processing稀疏末列維持固定欄寬與左上順序；inventory旁panel只顯示type capacity，不因hover改變。因 Slot.x/y final，client重建transform/machine slots時要委派原slot validation；off-page machine slots放`-9999,-9999`，panel-local wheel切頁後重建。
- **網路**:所有 network block 都以 block callback 為 authoritative path：`onRemove` 在 state 已替換後重建 old position，`moved=true` 也不可跳過；`onPlace` 將一般、指令/`setBlock`、活塞 final state 合併到 next-tick growth pass，批次放置同 component 只重建受影響 Core。不可只靠 `BreakEvent`/`EntityPlaceEvent`。`tryIncrementalAdd` 先用 cached connected set 守住與 full rebuild 相同的 depth/member boundary；bridge detached segment、多 Core、破壞仍 full rebuild。Chunk lifecycle 另外以 server-only FULL ticket transition 驅動：失去 FULL 時只先保留既有 `LevelChunk` snapshot，下一 tick 才從 snapshot 的 network boundary 與仍 loaded 的外側 bounded BFS 找 Core 並 full rebuild；`ChunkEvent.Load` 只接受 server `LevelChunk` 並 one-shot 排程，所有 level interaction 延到下一 tick，flush 以 non-loading `getChunkNow` 試一次後一律移除 queue entry，未就緒不逐 tick retry，後續 FULL ticket transition 再補排；同一 flush window 內未實際卸載就重新取得 FULL 時取消 pending unload，不額外重掃。Boundary 會先篩出兩側都仍是 loaded network block 的有效連接，再套用 `MAX_NETWORK_BLOCKS` 上限；絕不 force-load、也不做每 tick/週期性整網掃描。Unload 會自動移除遠端容量，reload 會自動恢復，multi-Core conflict 與完整拓樸語意不變。`bfsFindCore` / `bfsFindCorePositions` / full `rebuildNetwork` 都受 `NETWORK_SCAN_DEPTH` + `MAX_NETWORK_BLOCKS` 上限保護；達上限的Core保存`networkCapped`並在玩家直接互動時顯示action-bar警告，移除截斷member後full rebuild會清除狀態。Core的`neighborChanged`只對network block變化排scheduled tick，重複通知合併成一次full rebuild；封包 handler 包 `ctx.enqueueWork(...)` 並透過 menu 的 exact-Core resolver。

## RS2 Heuristics Adopted (2026-06-21)

完整對照見 `docs/rs2-design-gap.md`(該採用 vs 故意分歧)+ 計劃 `docs/superpowers/plans/2026-06-21-rs2-heuristics-adoption.md`。已採用(僅取模式):

- **fuzzy 配對(A5b)**:合成材料以 `Ingredient.test` 跨變體;preview/execute 共用 joint reservation plan,最後按實際 `ItemKey` 精確扣除(取代各 predicate 獨立 `countMatching` 後重複算同一批物品)。
- **Action/Actor + change events(A2/A3 foundation)**:storage mutation 都可帶 `Action` 與 `Actor`;execute insert/extract 會發 `StorageListener` delta event。P3 若要做 grid delta,應基於此 listener,不要再從 client 保存 storage state。
- **view 設定 server 同步(A5a)**:sort / order / search 模式為 server 權威、經 data slot 同步;終端按鈕標籤/tooltip 反映真實狀態(非 client 私有)。
- **選取物品身分化(A4)**:crafting 選取以 `ItemKey` 身分為準(經畫面外 `selectionContainer` slot 自動同步),非 grid slot index → 排序/捲動後配方面板不再亂指。
- **合成 preview(A7)**:用 simulate 路徑算「可做 N / 缺什麼」顯示,不異動狀態。
- **增量網路成長(A1,安全範圍)**:放置 callback 先 coalesce 到 next tick；單一方塊接到既有 connected set 時，`StorageCoreBlockEntity.tryIncrementalAdd` 用 cached-set bounded path check 確認不越過 full rebuild depth/member guard 後加入(不讀整個 world graph)。**破壞/批次/不確定拓樸一律 full `rebuildNetwork`**(移除可能分裂網路,放置若 bridge detached segment 或連到多個 core 也屬不確定)。`capacityOf()` 是兩條路徑唯一的容量計算來源;GameTest 守護 simple growth、programmatic placement、piston move、depth boundary、detached bridge full rebuild、multi-core bridge conflicted。
- **仍未採用(未來)**:**P3 增量 grid delta**(grid 改收差異、不整份重建)與完整常駐 network graph;目前分頁式 grid(≤81 格,vanilla 已增量同步)低價值,除非改成整列表 client grid 才值得。
